# 화면 정렬 맞추기 절차 (2026-10-01 상세보기 `✕` 정렬 작업에서 확정한 방식)

사용자는 "상세보기 제목 줄 가운데 정렬해줘", "버튼 그룹 오른쪽이 그리드에서 벗어났어"처럼 **짧게** 말한다.
원인 설명이나 방법 선택을 요구하지 않는다 — **재서 → 원인 찾고 → 가장 튼튼한 방법으로 고치고 → 숫자로 증명**한다.

## 0. 시작
- 모델: 단순 정렬은 **Sonnet**(CLAUDE.md 0장). 여러 파일·원인 불명이면 Opus. 한 줄로만 알린다.
- **되묻지 않는다.** 기준선(무엇에 맞출지)이 모호하면 가장 자연스러운 기본값을 고르고 "○○에 맞췄습니다"라고
  보고에 가정을 밝힌다. 사용자가 방향을 바꾸면 그때 고친다.
  (되묻는 건 안 되돌릴 일이 걸린 경우뿐 — 정렬은 되돌리기 쉽다.)
- 기본 기준선 고르는 법:
  - "그리드/내용/표" 에서 벗어났다 → **그 아래 내용 격자의 오른쪽·왼쪽 끝**
  - "가운데 정렬" → **같은 줄 가장 큰 요소(입력칸·버튼)의 세로 중심**
  - "간격" → CLAUDE.md 6-1 눈금(`gap` 2/4/6/8/10/12/20/22/28px)

## 1. 실측 — 반드시 먼저 (코드를 읽기 전에)
Chrome 도구(`mcp__claude-in-chrome__*`)로 **실제 화면**의 위치를 `getBoundingClientRect()`로 잰다.
- 가로 정렬 → 각 요소의 `left`·`right`. 세로 정렬 → 각 요소의 **중심 = top + height/2**를 줄 중심과 비교.
- **기준 요소와 어긋난 요소 모두**를 재서 표로 만든다(어긋남 = 요소 위치 − 기준 위치, px).
  어긋남이 한 곳이 아니라 **같은 모양 여러 곳**(섹션 제목 줄 전부 등)이면 전부 잰다.
- 창/상태가 다른 경우도 한 번 더 잰다(스크롤바 유무·창 폭·접힘/펼침).
- 상세보기 열기: `td.rt-detail-cell` 클릭 / 닫기: `button.modal-close` 클릭.
  리그 탭: 버튼 텍스트 클릭(`공식 데이터` → `EPL`). 개발 서버가 `localhost:5173`에 켜져 있다.

### 측정 환경 함정 (실제로 겪음)
- **탭이 화면에 안 보이는 상태(`document.visibilityState === 'hidden'`)면** 브라우저가 화면 갱신을 멈춘다 →
  `requestAnimationFrame`이 영원히 안 돌아 명령이 45초 시간 초과로 끊기고, `ResizeObserver`도 안 불리고, 스타일을
  바꿔도 레이아웃이 안 갱신된 것처럼 보인다. → **`tabs_create_mcp`로 새 탭을 열어서** 재고, `rAF`는 쓰지 않는다.
  (그래도 hidden이면 정적 위치 측정만 믿고, 동적 동작은 "확인 못 함"으로 보고한다.)
- 한 명령은 45초 안에 끝내야 한다 — 긴 반복은 나눠서 실행한다.
- 시험하려고 인라인 스타일을 바꿨으면 **반드시 원래대로 되돌린다.**
- 주소에 `?`가 든 문자열은 도구가 출력을 막으니, 필요하면 `new URL(...).pathname`만 찍는다.

## 2. 원인 찾기
어긋난 요소의 CSS를 읽는다(주로 `web/src/**/*.css`, 필요하면 JSX).
BETPRO에서 실제로 나온 원인 유형:

| 증상 | 흔한 원인 | 고치는 방법 |
|---|---|---|
| 제목·칩이 입력칸보다 위로 쏠림 | 줄 컨테이너가 `align-items: baseline`(글자 밑줄 기준), 입력칸만 `align-self:center` | 컨테이너를 `align-items: center`로(예: `.detail-section h3`, `.ts-band-head`) |
| 스크롤 영역 **밖** 요소(헤더 버튼)가 안쪽 내용보다 바깥으로 나감 | 안쪽 내용은 스크롤바 폭만큼 밀리는데 밖의 요소는 그걸 모름 | 스크롤바 폭을 `offsetWidth - clientWidth`로 재서 CSS 변수(`--xxx-sbw`)로 넘기고 `calc(여백 + var(--xxx-sbw, 0px))`. `ResizeObserver(scroller)`로 따라간다 |
| `absolute` 요소가 카드 여백과 안 맞음 | `right: 14px`처럼 하드코딩 vs 내용은 카드 padding 28px | 내용 쪽 여백 값과 같은 식으로 계산(`calc`)하거나 변수로 공유 |
| 항목 사이 간격이 들쭉날쭉 | 구분자를 텍스트 공백(`' · '`)으로 둠 — 연속 공백이 합쳐짐 | flex `gap`으로 벌린다(CLAUDE.md 6-2) |
| 내가 쓴 규칙이 안 먹음 | 같은 클래스가 `LeagueTable.css`에도 있고 **그 파일이 나중에 로드**돼 특이도 동률에서 짐 | 선택자에 상위 클래스를 붙여 특이도를 올린다(`.detail-modal-card .modal-close`) |

- **그 CSS 줄 위의 주석을 읽는다.** 이 앱은 "2026-09-12 사용자 지정 — …"처럼 이전 결정 이유가 주석에 있다.
  주석이 지킨 결정(예: 제목 줄 `margin-top:-8px` 등)을 깨지 않게 고친다.
- 같은 클래스를 **다른 곳에서도** 쓰는지 `grep`으로 확인한다(공유 규칙을 바꾸면 다른 팝업이 변한다).

## 3. 고치기
- **숫자 한두 개 맞춰 보기 금지.** 원인(기준이 달라서)을 없애는 구조적 수정을 우선한다.
  하드코딩 `px`는 CLAUDE.md 6-1 눈금 값일 때만.
- 영향 범위를 좁힌다: 대상 팝업/컴포넌트 클래스로 한정(`.detail-modal-card …`), 공용 규칙(`.modal-close`)은 직접 안 바꾼다.
- 새 CSS 주석에 **날짜 + 사용자 지정 인용 + 원인**을 한두 줄로 남긴다(앱 주석 관례).
- 상세보기를 건드렸다면 **스샷저장**(`handleScreenshot`, `html-to-image`)이 카드 스타일을 잠깐 바꿨다 되돌리는
  구조(`saved` 인라인 스타일 복구)와 부딪히지 않는지, 조작 버튼이 사진에서 빠지는 필터에 걸리는지 본다.
- 4장 **보호 대상**(`api/engine.py` 분석 함수)은 정렬 작업과 무관 — 건드리지 않는다.

## 4. 검증 — 같은 측정을 다시
1. **1단계와 똑같은 측정**을 반복해 전/후 표를 만든다(어긋남이 0px 또는 반픽셀 이내여야 한다).
2. 창/상태가 다른 경우(스크롤바 있음·없음, 접힘·펼침, 다른 경기·긴 제목)에서도 맞는지 본다.
3. **스크린샷**으로 눈으로 확인한다(사용자가 보는 것과 같은 화면).
4. `cd web && npx oxlint src/<수정한 파일>` 오류 0건.
5. 다른 곳이 안 변했는지: 같은 클래스를 쓰는 다른 팝업/화면 하나를 열어 본다.
6. 시험 때 바꾼 인라인 스타일·열어 둔 팝업·탭을 정리한다.

## 5. 보고 (CLAUDE.md 0-1 형식 — 짧게)
1. **바뀐 결과**: "고치기 전 → 지금" px 표(어디가 몇 px 어긋났고 지금 몇 px).
2. **어떻게 고쳤나**: 원인 한 줄 + 바꾼 파일/규칙(비개발자도 이해하게).
3. **검증한 것 / 못 한 것**: 못 한 것(예: 탭이 가려져 동적 동작 시험 불가)은 반드시 밝히고, 사용자가 직접
   확인할 곳을 번호로 안내한다.
4. **영향 범위**: 같은 클래스를 쓰는 다른 곳이 있는지.
5. 마지막에 "브라우저에서 확인해 보세요 / 커밋할까요?" — **커밋·푸시는 사용자가 시킬 때만**.

## 하지 말 것
- 재지 않고 CSS 숫자를 바꿔 보며 눈대중으로 맞추기.
- 방법 A/B를 길게 늘어놓고 되묻기(기본값을 고르고 가정을 밝힌다).
- 공용 규칙을 바꿔 다른 팝업까지 흔들기.
- 확인하지 못한 동작을 "됩니다"라고 말하기.
