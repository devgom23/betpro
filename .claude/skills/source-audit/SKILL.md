# 소스 점검 절차 (2026-09-30 3차 점검에서 확정한 방식)

사용자가 "소스 점검해줘"라고만 해도 아래 순서대로 한다. **감으로 짚지 않고, 재서 줄 세운다.**
(결과 상세·이력: 메모리 `project-audit-2026-09-30`, 이전 점검 `project-audit-2026-09-10`)

## 0. 시작할 때 (CLAUDE.md 0장 규칙)
- 어떤 모델이 좋은지 먼저 알린다 — 이 작업은 **Opus** (원인 모를 느림을 찾고 여러 파일을 건드림).
- 점검 방식을 한 번에 제안한다: 4단계 요약 + 범위에서 뺄 것. 사용자가 "진행"하면 시작한다.
  이미 "소스 점검해줘"로 시작했으면 길게 묻지 말고, 아래 단계를 짧게 알린 뒤 1단계부터 간다.
- 먼저 규모를 센다: `git log --since=<지난 점검일> --oneline | wc -l`, 늘어난 줄이 큰 파일 TOP.
  (지난 점검일은 메모리 `project-audit-*`에서 찾는다.)

## 1. 실측으로 병목 찾기 (코드는 건드리지 않는다)
**서버**: `python .claude/skills/source-audit/scripts/measure.py`
- 서버 함수 약 28개를 두 번씩(콜드·웜) 재고 웜 느린 순 TOP 10을 낸다. 서버를 따로 켤 필요 없다.
- 서버 주소가 새로 늘었으면 `scripts/_common.py`의 `endpoints()`에 한 줄 추가한다
  (`grep -n '^@app.get' api/main.py`로 빠진 것을 확인).
- 느린 항목은 `cProfile`로 원인 함수를 짚는다(`pstats` cumulative 상위, 프로젝트 파일만 거른다).

**화면(브라우저)**: Chrome 도구로 화면별 요청 수·완료 시간을 잰다.
- 측정 항목: 시즌분석 · EPL 리그 · 상세보기(여러 경기, **7~9초 쉬었다가**) · 이번주 리스트/픽 · 베팅내역 ·
  아카이브 · 기타경기(내 데이터) · 통합DB.
- 도구 안에서 `performance.getEntriesByType('resource')`로 `/api/` 요청만 모아 개수·길이·겹침을 본다.
- **같은 요청이 2번씩 나가면** 개발 모드 이중 실행(StrictMode)이나 중복 호출을 의심한다.

**측정 때 함정 (실제로 겪음)**
- 서버를 막 켠 직후엔 백그라운드 계산(`sample-dir`, `book-dir`, `axis-stats`)이 돌아 웜도 느리게 나온다 →
  CPU가 0이 될 때까지(5초 CPU 사용 ≈ 0) 기다린 뒤 잰다.
- **쉬었다 재야 보이는 병목이 있다**(5초 기억이 만료되는 것) — 연달아 두 번 재면 안 나타난다.
- 브라우저 탭이 뒤에 있으면 타이머·렌더가 늦춰져 시간이 부풀고, 한 명령이 45초를 넘으면 시간 초과로 끊긴다 →
  한 번 열 때마다 명령을 나누고, 긴 반복은 `window.__x` 에 쌓아 두고 따로 읽는다.
- 브라우저 도구가 `?`가 든 주소 출력을 막으니, 주소는 `new URL(...).pathname`만 찍는다.

## 2. 규칙 위반 훑기 (읽기만)
CLAUDE.md 3장 캐시 규칙을 새 코드가 지키는지 `grep`으로 본다.
- DB에 쓰는 곳이 `with DATA.table_write(db, 테이블):`로 감쌌는가 (`to_sql(`, `INSERT`, `UPDATE`, `DELETE FROM`).
- 캐시된 표를 **`.copy()` 없이 고쳐 쓰는가** (`load_league_df*` 결과에 `df[...] =`, `df.at/loc[...] =`).
- 리그 표를 우회해 `_read_table`/`attach_for_league`를 직접 부르는가.
- 요청마다 리그 전체를 훑는 표(키→행번호 등)를 `cached_derive` 없이 지역 변수로 만드는가.
- 요청마다 무거운 확인(43만 줄 `MAX`/`COUNT`)을 하는가 → `multibook_odds.mb_state` 재사용 대상.
- 화면: `useEffect` 중복 요청, 빈 목록을 "불러오는 중"으로만 두는 곳(무한 로딩처럼 보임).
- 4장 **보호 대상**(`api/engine.py`의 분석 함수)은 점검 대상에서 빼고 절대 고치지 않는다.

## 3. 보고서 (코드 수정 전에 사용자에게)
다음 표를 낸다 — 쉬운 말로, 새 용어는 먼저 풀어서(CLAUDE.md 0-0).
1. **화면별 실측표**: 화면 · 요청 수 · 다 뜨기까지 시간.
2. **개선 후보 표**: 기호(A, B…) · 원인 · 기대 효과(몇 초→몇 초, 추정이면 추정이라고) · 위험도.
3. **규칙 점검에서 이상 없던 것**과 **보류를 권하는 것(이유 포함)**.
4. 추천 순서와 함께 "어떤 것을 진행할까요?"로 끝낸다. **사용자가 고른 것만** 고친다.
   (사용자가 "네가 계획대로 진행해"라고 하면 추천 순서대로 진행.)

## 4. 수정 → 값 대조 (필수)
수정 **전에** `snapshot.py save before`로 결과 값을 저장한다. 같은 코드로 한 번 더 저장해 결과가 매번
같은지(결정적인지) 확인한 뒤 기준으로 쓴다.
수정 후 `snapshot.py save after` → `snapshot.py diff before after` → **모든 항목 같음**이어야 한다.
- 표본·판정처럼 계산이 바뀌는 수정은 `git show HEAD:api/main.py`로 옛 코드를 임시 파일에 받아 **새 코드와
  여러 경기(공식 + 내 데이터)를 나란히 돌려** 비교한다(어제 46경기).
- 새 **기억 장치(캐시)**를 넣으면 반드시 "자료가 바뀌면 낡은 값이 안 남는가"를 따로 시험한다
  (임시 파일/복사본 DB로 — **실제 `master.db`/`multibook.db`에는 쓰지 않는다**).
- 프론트: `cd web && npx oxlint src/` 오류 0건(기존 경고는 구분).
- 브라우저로 같은 화면을 다시 재서 전후를 비교한다.
